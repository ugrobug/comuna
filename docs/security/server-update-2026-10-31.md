# Обновление безопасности серверов, 31 октября 2026

Релиз приложения: `2fc4996`. Область: production Тамбура (Ubuntu 24.04/OpenVZ,
Docker Compose) и VPS с Amnezia/Telegram relay (Ubuntu 26.04/KVM).
PHP/PHP-FPM и Apache в запущенных службах/контейнерах этих двух серверов не
обнаружены. WordPress на Beget и инфраструктура TLS/виртуализации провайдеров
в эту проверку не входят.

Установлены 155 системных обновлений на Джино и 20 обновлений + 8 новых
пакетов ядра на VPS. `dpkg --audit` после установки пуст на обоих серверах.
Нестандартная ссылка `/etc/localtime -> .../Host` на Джино мешала настройке
`tzdata`; заменена на `Etc/UTC`, соответствующий `/etc/timezone`, затем
успешно выполнен `dpkg --configure -a`. Во время обновления SSH шлюз Джино
временно не принимал соединения; использован прямой адрес с проверкой
того же host key. Исходный SSH-шлюз затем снова проверен успешно.

MySQL используется в коде только инструментами `legacy_migration`, а не
чтением лент/постов или проверкой WordPress-паролей. На момент проверки
подключений миграционного пользователя не было. Создан SQL dump базы
через прикладного пользователя; вход root по старому env-паролю не
работал. Том и остановленный контейнер сохранены. Обычный compose up
больше не запускает эту EOL-службу. Для будущего импорта сначала переносить
dump в поддерживаемую СУБД в изолированном окружении; не включать профиль
legacy-migration как постоянную production-службу.

## Зависимости и границы проверки

- `npm audit`: 27 замечаний (14 high, 9 moderate, 4 low) → 5 low,
  без high/moderate/critical. Обновлён lockfile в пределах текущих диапазонов;
  `npm audit fix --force` не применялся.
- Остаточные low: два advisory SvelteKit и цепочки build-зависимости
  `deepmerge`. В проекте не найдены `use:enhance` и включённый prerender,
  необходимые для описанных сценариев SvelteKit. У deepmerge опубликованного
  исправления нет; в этом проекте он используется инструментами сборки.
  Это оценка применимости, а не отсутствие advisory. Миграция на SvelteKit 3
  меняет API/конфигурацию и должна проверяться отдельно.
- `pip-audit` по точному списку 45 production Python-пакетов: известных
  уязвимостей не обнаружено. Runtime Python 3.12.16, Django 5.2.18.
- `govulncheck -mode=binary` нового AmneziaWG: 0 уязвимостей в используемых
  символах/импортируемых пакетах. Отмечены 37 advisory в требуемых модулях,
  уязвимый код которых сканер не обнаружил в используемом пути. Это не
  доказательство безопасности всех исходников/неиспользуемых функций.
- HAProxy relay 3.2.26 / Alpine 3.24.3 уже актуален, конфигурация сохранена.
- В образах backend и PostgreSQL доступен только новый `tzdata` 2026f;
  это обновление часовых зон, не обнаруженная уязвимость. На VPS
  `qemu-guest-agent` оставлен пакетным менеджером отложенным.
- Ядро Джино `6.8.0` принадлежит OpenVZ-хосту провайдера. Внутри контейнера
  нет пакетов ядра/идентификатора полного исправленного билда. Подтвердить
  исправления гипервизора и внешнего TLS-прокси может только Джино.
  Не считать номер `6.8.0` доказательством ни уязвимости, ни исправления.

## Amnezia и восстановление

Сохранены клиентские ключи, конфигурации, UDP-порты и имена контейнеров.
AmneziaWG userspace пересобран из официального `v3.1.20260828`, commit
`b5928efb6ca19f0153958460c3d141f04abc5c2e`, на Go 1.27.3.
Новые контейнеры предварительно проверены без внешних портов.

Ubuntu AppArmor `wg-quick` блокировал Alpine BusyBox и нестандартный путь
конфигурации. В `/etc/apparmor.d/local/wg-quick` добавлены разрешения
на необходимые исполняемые файлы и `/opt/amnezia/wireguard/`; профиль
не отключался. В новый WireGuard-образ добавлен userspace fallback.
После перезагрузки оба интерфейса поднялись; у AWG2 наблюдались свежие
handshake двух клиентов. У обычного WireGuard есть два настроенных peer,
но свежих клиентских handshake не было — клиентское подключение именно
этого протокола не подтверждено.

Telegram relay стартовал автоматически, SSH-туннель восстановился,
`python -m telegram_integration.health` завершился успешно. Логи контейнеров
VPN теперь ограничены 2 × 5 MiB на контейнер.

## Резервные копии и откат

На каждом сервере `/var/backups/tambur-security-20261031`, доступ root:
пакеты/конфигурации, inspect контейнеров; на Джино PostgreSQL dump/globals,
MySQL dump и env, на VPS — экспорт и снимки обоих VPN-контейнеров.
Архивы и VPN-образы содержат секреты: не публиковать в Git/registry.

- Прежние app images: `tambur-backup/<container-name>:20261031`.
  Для отката образов задать их в отдельном compose override, выполнить
  up -d и restart nginx; приложение откатывать отдельным revert-коммитом.
  После записи данных в новую PostgreSQL minor-версию не подменять
  автоматически каталог данных старым dump: это потеряет новые записи.
- Прежние VPN-контейнеры сохранены с суффиксом
  `-before-security-20261031`, restart=no; образы
  `<name>:security-backup-20261031`. Остановить новый контейнер, вернуть
  прежнему имя/политику запуска и стартовать. Не запускать два экземпляра
  на одних внешних портах. Ключи/конфигурации повторно не генерировать.
- Предыдущее ядро VPS осталось установленным для загрузки через консоль.
- Регулярно сверять версии с advisories и пересобирать закреплённые образы:
  фиксация версии даёт воспроизводимость, но не автоматическое обновление.
  Один `compose up --build` не обновляет все внешние образы сам по себе.

## Дополнительная служба: Zabbix Agent

При финальном обходе слушающих портов VPS обнаружен агент из отдельного пакета провайдера
`zabbix-agent-timeweb`: `Zabbix Agent 5.0.3rc1` (сборка июля 2020), TCP 10050. Подготовлен и
запущен Zabbix Agent **6.0.49 LTS** из официального исходного архива,
проверенного по опубликованной SHA-256. Выбрана поддерживаемая LTS-ветка
для совместимости старой агентской конфигурации, без установки сервера,
PHP-интерфейса или новой базы мониторинга. Сборка использует системные
OpenSSL/PCRE2. Старые бинарник и конфигурация сохранены в каталоге backup.

Runtime: `/opt/zabbix-6.0.49/sbin/zabbix_agentd`, systemd drop-in
`/etc/systemd/system/zabbix-agent.service.d/security-runtime.conf`.
Сохранены User/Group=zabbix, исходный конфиг и адреса разрешённых серверов.
`agent.ping` с этим конфигом вернул 1; служба активна. Получение метрик
удалённым сервером провайдера отдельно не проверялось. Этот runtime
нужно обновлять отдельно: стандартное обновление пакета провайдера не
заменяет наш versioned-бинарник. Пакет провайдера и его исходный бинарник
оставлены для отката; запущенный процесс использует путь `/opt/zabbix-6.0.49/`.
Откат: восстановить старый бинарник из root-only backup, убрать созданный
drop-in, выполнить daemon-reload и restart zabbix-agent.

[Официальный релиз Zabbix 6.0.49](https://www.zabbix.com/rn/rn6.0.49),
[исходные архивы и контрольные суммы](https://cdn.zabbix.com/zabbix/sources/stable/6.0/).
