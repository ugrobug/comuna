# Unit Game на Тамбуре

Источник: `ugrobug/suphub`, commit `45957eecf3e65197b57ea53e14aa3cd1fb4610ba`.
Каталог `unitgame_app` перенесён в `backend/unitgame_app` без изменения всех 69
исходных файлов. Правила, интерфейс, изображения, обучение, localStorage,
ссылки для шаринга и исходный счётчик Метрики сохранены буквально.
Статистика из localStorage старого домена автоматически не переносится.

## Подключение

- `/s/unitgame` перенаправляет на `/s/unitgame/`, сохраняя query string.
- Nginx направляет `/s/unitgame/` в Django: исходные тонкие views рендерят
  меню, игру и обучение. Авторизация, SQL и API Тамбура игре не нужны.
- Приложение зарегистрировано в Django; namespace сохранён, поэтому ссылки
  меню автоматически получают новый префикс.
- Оригинальный относительный путь `../../static/unitgame_app/main.js`
  из `/s/unitgame/play/` и `/s/unitgame/onboarding/` разрешается в
  `/s/static/unitgame_app/`. Узкий nginx alias обслуживает эти модули;
  исходные абсолютные пути CSS и изображений остаются `/static/unitgame_app/`.
- В меню спецпроектов добавлена ссылка с полной загрузкой страницы, чтобы
  SvelteKit не перехватывал переход на Django-приложение.

Это интеграция существующего приложения, без рефакторинга его функций в классы:
сохранение исходной игры — прямое требование пользователя. Новая бизнес-логика
не вводится. Рабочий процесс игры полностью в браузере; сервер рендерит
ограниченный шаблон (2.6–10.7 KB HTML) и раздаёт неизменные файлы (~844 KiB
дискового пространства). При росте посещаемости в 10 раз растёт число отдач
страниц и ресурсов, а не стоимость запроса по размеру базы; постоянные
инфраструктурные расходы не меняются. Новые кеши, workers и сервисы не нужны.
Существующие политики безопасности nginx наследуются игровыми маршрутами.

## Выпуск и откат

Собрать frontend/backend по Deploy Playbook. Миграций схемы нет (в импортированном
каталоге migrations только `__init__.py`). После сборки выполнить
`python manage.py collectstatic --noinput` в backend: nginx читает ресурсы из
общего static volume. Проверить `nginx -t`, перезапустить nginx после пересоздания
контейнеров, проверить все три страницы игры, оба адреса ресурсов, главную,
реальный пост и API статуса книги. Не очищать общий кеш ради замера.

Откат: revert коммита подключения, повторить сборку и restart nginx. Схема и данные
БД не меняются; оставшиеся файлы static безопасны. Пользовательские локальные
изменения аналитики и киношаблона не входят в эту изолированную рабочую копию.

## Дополнительные события, 2026-10-18

В пул добавлены пять событий: уход конкурента (посещаемость +15%), снижение
рекламных ставок (CAC −4 ₽), инфляция поставщиков (себестоимость +4 ₽,
постоянные расходы +10 ₽/мес), крупный конкурент (посещаемость −10%,
конверсия −0,1 п.п.) и рост онлайн-рынка (посещаемость +10%, CAC +2 ₽).
Два исходных события, частота выпадения, обычные карточки и оформление сохранены.
События меняют текущие показатели при подтверждении и затем участвуют в расчёте
месяца; автоматического возврата к прежним значениям нет. Процент посещаемости
считается от текущего значения с округлением до целого. Существующие ограничения
не позволяют расходам и конверсии стать отрицательными.

Использован существующий формат данных и обработчик событий: дополнительных
прикладных объектов, запросов к БД или HTTP, изображений и инфраструктуры нет.
Пул вырос с 2 до 7 объектов, модуль — с 920 до 2651 байта. Перемешивание пула
остаётся O(n), вычисление эффектов одного события — O(1); при 70 событиях
растёт размер модуля и пула, а не число запросов. Версии адресов модуля и его
точки входа обновлены для сброса браузерного кеша.

Проверка через настоящий обработчик игры в JSDOM: пять сценариев с итоговыми
метриками и балансом после месячного расчёта, нижние границы показателей,
выпадение всех семи событий без повторов. На одном локальном окружении медиана
пяти серий по 10 000 выборок и вычислений эффекта: 0,000212 мс (2 события),
0,000217 мс (7), 0,000212 мс (70); бюджет <1 мс выполнен. Это микрозамер
выбора события без отрисовки, не LCP/INP и не production p95. Серверные запросы
не изменены. Для отката — revert коммита событий и обычный выпуск с collectstatic
и перезапуском nginx, без миграций.

## Доступность решений при малых постоянных расходах

При `fixed < 20` не предлагаются решения, у которых хотя бы одна кнопка
снижает `fixed` сразу или после расчёта месяца. При ровно 20 ₽ ограничения нет.
Проверяются вычисленные эффекты, включая формулы, через тот же `resolveEffects`,
который используется при принятии решения. В текущей колоде условие затрагивает
12 из 53 карточек; глобальные события не фильтруются.

`DecisionDeck` хранит очередь решений и получает колоду, перемешивание и расчёт
эффектов явно через конструктор. `nextTurn` только запрашивает карточку для
текущего состояния. Пропущенные карточки остаются в очереди и снова доступны
после роста расходов; при исчерпании доступных решений начинается новый цикл.
Выбор ограничен двумя проходами по колоде; пустая или полностью недоступная
колода вызывает явную ошибку конфигурации вместо бесконечного перебора.
Память и худшая стоимость выбора O(n), новых запросов БД и фоновых задач нет.
Браузер загружает один дополнительный небольшой JS-модуль; адрес точки входа
обновлён, чтобы правило применилось после перезагрузки страницы.

Проверки: `npx vitest run tests/unitgameDecisionDeck.test.js` (12 тестов),
Django integration tests (5), production build. Дополнительно настоящий цикл
игры проверен в JSDOM при 0 / 19 / 19,99 / 20 ₽ и после перезапуска.
Локальный микрозамер: медиана пяти серий по 10 000 выборок при `fixed=0` —
0,000040 → 0,000996 мс для 53 карточек и 0,000037 → 0,006914 мс для 530.
При `fixed=20`: 0,000020 → 0,000032 мс для 53 и 0,000031 → 0,000051 мс для 530.
Бюджет выбора <1 мс выполнен; это CPU-замер без DOM и сети, не LCP/INP или p95.
Оформление, иллюстрации, эффекты решений и частота глобальных событий сохранены.
Откат: revert изменения и обычный выпуск с collectstatic и restart nginx;
миграций и изменений сохранённых результатов игры нет.
