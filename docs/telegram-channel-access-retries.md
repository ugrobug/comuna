# Повторная проверка доступа при импорте Telegram

## Инцидент 25 сентября 2026

У nanya_knitting сохранена активная привязка, включена автопубликация без задержки,
бот остаётся администратором. Запросы getChat/getChatMember с production неоднократно
заканчивались сетевым тайм-аутом, после чего повторная попытка возвращала успех.
Публикации 235 и 236 от 21 и 24 сентября отсутствовали. Пост 234 был удалён вручную
на сайте, поэтому восстановлению не подлежит.

Найден подтверждённый дефект: `_is_bot_admin` возвращал False и при реальном отсутствии
прав, и при недоступности Telegram. Обработчик завершался успешно, polling подтверждал
update и больше его не повторял. Это вероятная причина пропущенных публикаций;
исторические логи не содержат идентификаторов отвергнутых update для точной атрибуции.

## Изменение

`TelegramChannelAccessVerifier` инкапсулирует проверку доступа. Источник идентификатора
бота и HTTP opener передаются явно. Для импорта включается строгий режим; интерактивные
команды бота сохраняют прежний контракт. Проверка не требует права отправлять сообщения
в канал: для чтения достаточно статуса администратора.

- Подтверждённые member/left/kicked/restricted и ответы API 400/403 означают отказ.
- Сетевой сбой, 429/5xx, некорректный JSON, отсутствие статуса или идентификатора бота
  вызывают TelegramAccessCheckUnavailable без URL/токенов в сообщении исключения.
- Существующий TelegramUpdateProcessor сохраняет cursor и повторяет update.
- Существующая уникальность author/message_id предотвращает создание дубликата.

На успешную обработку приходится один getChatMember с timeout 5 секунд; добавочных
SQL-запросов нет. Память O(1) на проверку, количество проверок O(N) по числу update.
При росте потока в 10 раз ограничением остаётся последовательный polling и Telegram API.
Новой инфраструктуры и кеша прав нет. При продолжительном сбое очередь задерживается:
это исправление предотвращает подтверждение потерянных сообщений, но не заменяет
долговечный inbox и не гарантирует восстановление за пределами хранения update Telegram.

## Проверка

67 тестов telegram_integration прошли, включая тайм-аут → повтор → один пост,
подтверждённое отсутствие доступа, 400/403 против 429/5xx, повреждённые ответы,
импорт альбомов и конкурентную обработку. Django check и frontend build проходят.

Локальный PostgreSQL, по 10 текстовых постов после одинакового прогрева, Telegram
заменён управляемыми ответами, без кеша ответа:

| Версия | Время | SQL | Время SQL | Проверки прав |
| --- | ---: | ---: | ---: | ---: |
| До | 64,92 мс | 230 | 3 мс | 10 |
| После | 67,85 мс | 230 | 2 мс | 10 |

Это отдельные наблюдения, не p95 и не замер сетевого Telegram. Стоимость запросов
не увеличилась; разница локального времени около 3 мс на десять операций.

## Выкатка и откат

Миграций нет. После релиза проверить HTTP основных страниц, права бота, наличие
восстановленных публикаций и события polling без вывода пользовательского контента.
Восстановление двух публикаций выполняется отдельно, идемпотентно, с сохранением
исходных дат и локальных вариантов фотографий. Журнал созданных ID хранится вне Git
на сервере. Код откатывается revert коммита; восстановленные публикации сохраняются.
