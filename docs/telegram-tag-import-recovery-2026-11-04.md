# Восстановление импорта Telegram: 4 ноября 2026

## Причина

При диагностике отсутствующих изображений все 79 заданий фотографий оказались
успешно завершены: в последних обработанных постах есть HTML изображений и превью.
Пользователь подтвердил, что изображения появились. Резерв S3 работал, на диске
оставалось 4,1 ГБ. Но обнаружилась отдельная остановка приёма следующих обновлений:
`IntegrityError`, ограничение `feeds_tag_name_key`. Heartbeat был свежим, однако
успешный цикл отсутствовал около 14 часов. Курсор сохранялся на проблемном сообщении.

Присвоение тегов сопоставляло их по сохранённой лемме. Если текущий результат
морфологического разбора отличался (в том числе когда анализатор недоступен),
существующее уникальное имя не находилось по лемме. Следовал повторный INSERT,
транзакция поста и очереди фото откатывалась. Такая же ошибка возникала при
одновременном создании одного тега двумя импортами.

## Изменение

Код `bab7890`: точечное исправление существующего пути записи тегов. На промахе
по лемме вместо безусловного создания используется ORM `get_or_create` по
уникальному имени; лемма задаётся только для нового тега. Существующие свойства
модерации не перезаписываются. Django обрабатывает конкурентный INSERT через
savepoint и повторное чтение, сохраняя внешнюю транзакцию работоспособной.

Прикладной сервис `TelegramChannelImport` и транзакционная очередь фотографий
сохраняют прежние обязанности. Новые архитектурные слои, инфраструктура и миграции
не нужны. Прежнее сопоставление разных написаний по общей лемме сохранено.

## Проверки

До исправления 3 из 4 новых тестов воспроизвели `feeds_tag_name_key`: изменённая
лемма, отсутствующий анализатор, два конкурентных импорта. После исправления
179 тестов прошли, включая Telegram, согласования, резервное хранилище, API тегов
и новую проверку «пост с существующим тегом → очередь фотографии → изображение
и превью → следующий пост». Точный изолированный релиз также прошёл npm build
и Django check. Другие незавершённые локальные изменения в релиз не включены.

Локальный PostgreSQL, 501 тег, по 30 последовательных выполнений, внешних API нет:

| Сценарий | До: медиана / SQL / ошибок | После: медиана / SQL / ошибок |
|---|---|---|
| Обычный тег | 5,77 мс / 4 / 0 | 6,70 мс / 4 / 0 |
| Имя есть, лемма отличается | 5,76 мс / 4 / 30 | 7,15 мс / 5 / 0 |

Медиана времени SQL: 3,5 → 4,0 мс и 4,0 → 4,5 мс соответственно (округление
журнала). Исправленный сценарий добавляет один поиск по уникальному индексу имени.
Максимум после исправления 9,21 и 12,02 мс. Это не production p95 и не нагрузочное
испытание. HTML/API ответа операция присвоения тегов не формирует; HIT/MISS,
гостевой/авторизованный первый экран здесь неприменимы.

Существующий подбор автоматических тегов всё ещё читает каталог тегов целиком;
его время и память растут с каталогом. Эта потеря не введена исправлением. При
росте каталога в 10 раз потребуется отдельное измерение и переработка подбора;
индекс имени ограничивает только добавленный путь разрешения коллизии. Массовый
рефакторинг подбора тегов в аварийный релиз не включён.

## Выпуск и откат

Релиз без миграций: push, pull, compose up --build, обязательный restart nginx.
Проверка после запуска: heartbeat и успешный цикл polling, отсутствие ошибок
фотографий, продвижение очереди, HTTP 200 главной/поста/API и изображений.
Откат одного изменения кода возможен без изменения данных, но возвращает ошибку
повторного имени. Нельзя сбрасывать ожидающие обновления Telegram ради обхода ошибки.

## Результат production

Код `bab7890` выпущен: push/pull, compose up --build и restart nginx завершены,
Django check прошёл. После выпуска число завершённых заданий фотографий выросло
с 79 до 93; ожидающих и ошибочных заданий в проверенной выборке состояний нет.
Polling снова выполняет успешные циклы (последний за 5,2 с до проверки), ошибка
и blocked state отсутствуют. У последних трёх постов есть изображения и превью.
Два последних резервных изображения отвечают 200 за 13,23 и 1,19 мс до чтения.

Главная, пост 4492 и API `/api/special-projects/book/status/` отвечают 200:
TTFB 2,0 / 253,1 / 237,0 мс; объём 149237 / 71549 / 4351 байт. Это единичные
гостевые наблюдения после перезапуска, состояние кеша не фиксировалось; они не
подтверждают p95 или первый экран. Проверка скорости затронутой операции до/после
проведена локально выше; на production дополнительно подтверждено реальное
продвижение ранее остановленной очереди без обхода правил согласования.
