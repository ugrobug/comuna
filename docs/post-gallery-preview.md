# Галереи в превью и полноэкранном просмотре

## Поведение

Если первым изображением поста служит галерея, карточка показывает сетку максимум из четырёх снимков. Остаток обозначается `+N`; при открытии доступны все снимки этой галереи в исходном порядке. Обычная первая картинка, явно выбранная обложка и обложки шаблонов сохраняют прежнее поведение. Миниатюры компактного/списочного вида остаются компактными.

Полноэкранный просмотр открывается на нажатом снимке, поддерживает стрелки на экране, клавиши ←/→, Escape и горизонтальные свайпы. Перелистывание замкнуто внутри выбранной галереи. Вертикальное движение, мультитач и панорамирование в увеличенном режиме не переключают снимки. Клик по самому изображению не закрывает просмотр. Панель управления расположена поверх мобильного меню с учётом safe area.

## Архитектура и стоимость

- `PostPreviewGallery` выбирает первую галерею из EditorJS JSON/base64 или HTML. `LeadingGalleryParser` сохраняет границу HTML-галереи, включая вложенные контейнеры. Расчёт происходит при сохранении `Post`, вместе с существующими preview-полями.
- `Post.preview_gallery` хранит только URL/alt выбранной галереи. API добавляет необязательное поле `preview_gallery`, не меняя прежние `preview_image_url`, `thumbnail_url`, текст карточки и social image. Мобильное приложение может продолжать использовать прежние поля.
- Сериализация использует уже загруженное поле строки Post. Нет отдельных запросов, повторного разбора полного тела или проверок файлов во внешнем хранилище. URL проходят существующую проверку публичных изображений. Адреса уменьшенных копий рассчитываются только для первых четырёх снимков.
- `PostGalleryPreview` выводит четыре ленивые миниатюры до 640 px. Остальные оригиналы браузер запрашивает при переключении в просмотре. Размер сетки определён заранее, что предотвращает сдвиг карточки при загрузке.
- `PostGallery` отвечает за повторно безопасное преобразование галереи в полном тексте и сохраняет `data-expandable-src` в миниатюрах. `GallerySwipe` инкапсулирует состояние жеста; компонент просмотра только передаёт события и меняет текущий снимок.

Количество SQL не зависит от числа изображений. Передаваемые метаданные и время сериализации линейны по количеству снимков **первой** галереи ограниченной страницы постов. Сами файлы первого экрана ограничены четырьмя на карточку. При росте галереи в 10 раз растут метаданные, но не число изначально отображаемых изображений. Очень большие галереи остаются ограничением: следующий шаг при их реальном появлении — отдельное пагинируемое чтение списка изображений по нажатию, без усечения доступных пользователю фотографий. Новый кеш, индекс или сервис не нужен. Значение по умолчанию задано также в БД, чтобы старая версия приложения могла создавать посты во время переключения контейнеров.

## Проверка

Локальная PostgreSQL, Python 3.14, Node 25; 2026-09-30/10-01. Успешны:

- `npm run build`, Django system check, проверка соответствия модели миграциям.
- 36 Django-тестов: превью, сохранение/удаление галереи, перенос старых данных, лента для гостя/авторизованного пользователя, видимость, порядок и бюджет запросов. Новая проверка использует 10 разных авторов и сообществ, DummyCache; оба пути укладываются в 30 SQL.
- 4 Vitest-теста: порядок/оригиналы/повторная инициализация галереи; направления свайпа, порог, вертикальное движение, мультитач, zoom, смена/отмена контакта.
- В браузере на локальной production-сборке: превью из 6 снимков, открытие второго/четвёртого, переход к пятому, клавиша →, экранные стрелки, Escape, отдельная галерея из 3 снимков в теле, мобильная ширина 390×844 и видимость панели поверх нижнего меню. Физический свайп в Safari на iPhone не проверен — жесты проверены автоматическими тестами.

Изолированная сериализация полей изображений (`_serialize_post_preview_image_fields`), одинаковые синтетические посты с 10 изображениями, по 30 повторений; медиана, не p95 страницы:

| 10 | 0,903 | 6,406 | 2 251 / 13 361 | 0 / 0 |

До передавалась только одна фотография; дополнительная стоимость после — URL и подписи всей галереи. Время SQL внутри этого измерения равно нулю. Это локальный тест сериализации объектов в памяти без кеша ответа, а не измерение полного API, HIT/MISS production или LCP/INP.

Рост до 100 фото на галерею (30 повторений): 10 карточек — медиана 44,793 мс, 87 161 байт; 30 карточек — 134,860 мс, 263 621 байт; 0 SQL. Максимумы — 46,192 и 140,279 мс. Нагрузочный тест staging/production не проводился. Браузерная проверка использовала локальные тестовые SVG, поэтому не подтверждает скорость загрузки реальных фотографий по мобильной сети.

## Выпуск и откат

Миграция `feeds.0178_post_preview_gallery` добавляет поле и заполняет его для существующих постов. Пакеты по 100 строк, отдельные короткие транзакции, блокировки строк защищают от перезаписи параллельного редактирования; обновляются только строки с галереями. Первый запрос пользователя не запускает перенос. До релиза выполнить общий Deploy Playbook; после релиза — несколько безопасных проверок реальных галерей и времени API. Нагрузка и очистка общего кеша не требуются: действуют прежние TTL ответов.

В текущей задаче production не изменялся. При откате приложения можно оставить дополнительное поле в БД: прежняя версия его игнорирует. После остановки новой версии допустим обратный откат миграции; исходный контент постов не изменяется, поле можно восстановить повторным переносом.
