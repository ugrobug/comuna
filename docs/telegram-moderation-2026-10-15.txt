Telegram: согласование публикаций, 2026-10-15

Статус: исправление подготовлено локально, не выложено.
База сравнения: 409480d. Production-данные не изменялись.

Диагностика
У @TheStartupFather auto_publish=False, admin_chat_id заполнен, задержка 0.
Пост 27305 создан 08:27:40 UTC, updated_at=08:35:30 UTC, сейчас опубликован.
В старом коде нет аудита решения: по updated_at невозможно доказать, какой
обработчик снял ожидание и был ли пост публичным до нажатия пользователя.
В окне 08:20–08:30 UTC подтверждены повторные ошибки проверки доступа и загрузки
медиа, удерживавшие общий последовательный polling. Пользователю запрошено
уточнение о том, где именно был виден пост до подтверждения.

Воспроизведённые дефекты
1. Ручная пересылка копировала auto_publish из BotSession в уже настроенный Author.
   При Author.auto_publish=False и старом BotSession.auto_publish=True следующий
   импорт становился публичным. Старый обработчик воспроизведён из git в тестовой
   БД; новый оставляет режим канала и is_pending=True.
2. Повторное событие назначения бота администратором также могло сбросить режим.
3. Отсутствие admin_chat_id обходило согласование (либо давало None вместо bool).
4. Сбой более раннего channel_post блокировал обработку кнопок согласования
   в той же полученной пачке. После публикации запрос согласия не редактировался;
   сетевой сбой answerCallbackQuery оставлял старые кнопки и индикатор ожидания.
5. Старые approve/reject не проверяли текущего администратора и не блокировали
   запись от одновременных противоположных решений.
6. Материализованная лента не проверяла актуальные is_pending/is_blocked/
   publish_at у ранее включённой записи. Это защитный дефект, а не доказанное
   объяснение первой публикации нового поста.

Решение и ответственность
TelegramPostModeration — прикладной сервис: одна запись Post под блокировкой,
проверка actor_id/private chat и текущего admin_chat_id, единственный переход
из ожидания, сохранение telegram_moderation в raw_data (state, actor_id, decided_at).
Повтор не меняет решение. Одобрение сохраняет задержку публикации. Язык уже
определён при импорте; повторное определение и удаление перевода исключены.
TelegramModerationReceipt — адаптер Telegram: редактирует исходный запрос,
удаляет кнопки, показывает результат. Сетевые операции выполняются после commit.
Тайм-аут, 429/5xx и некорректный ответ дают исключение и повтор через polling.
Повтор editMessageText идемпотентен; message is not modified считается успехом.
Удалённое/недоступное сообщение — терминальный исход со сводкой в журнале.

TelegramUpdateProcessor сначала обрабатывает approve/reject в полученной пачке,
затем подтверждает исходную последовательность. Курсор не перескакивает через
ошибочный импорт. Успешные решения помнит только до продвижения курсора; после
рестарта безопасность повтора обеспечивает сохранённое состояние Post.
Другие callbacks сохраняют прежний порядок. Лимит getUpdates явно равен 100.
Память ограничена полученной пачкой, нет нового worker/брокера/постоянной очереди.
Если backlog занимает всю пачку, более поздняя кнопка ещё не будет получена.

TelegramChannelPostWriter сохраняет аудит при редактировании и блокирует уже
существующую запись. Альбомы сохраняют прежнюю блокировку Author/Post.
Согласование не отключается из-за отсутствия адресата. Сессия используется только
при первой привязке и не может включить автопубликацию поверх существующего
режима согласования. После ручной пересылки текст отражает реальный статус.
Публичная материализованная лента повторно проверяет доступ и срок публикации.
API web/mobile не меняется. Миграций и новой инфраструктуры нет.

Проверки
110 тестов Telegram и публичной ленты прошли за 4.748 с, включая:
- импорт/изменение, альбомы, пропадание доступа, повтор обновления;
- сохранение настройки при пересылке и повторном добавлении администратора;
- невидимость pending в детали, ленте автора/сообщества и старой материализации;
- проверку полномочий, отказ, повтор, задержку, сохранение аудита после правки;
- сбой доставки результата без повторной публикации;
- приоритет решения при ошибке импорта без пропуска offset;
- одновременные approve/reject на двух соединениях PostgreSQL: один переход.
Отдельно 2 проверки базовой версии и стоимости прошли. Django check,
npm run build, git diff --check успешны.

Производительность
Локальная PostgreSQL, 20 одинаковых коротких постов на вариант, сеть заменена
ответами в памяти, кеш ответа отсутствует. Полный callback до/после:
медиана 3.13 -> 4.86 мс, SQL-вызовы 6 -> 11, медиана SQL 0.5 -> 1.0 мс.
Увеличение связано с транзакцией, блокировкой и сохранением аудита через обычный
Post.save со штатными сигналами. Бюджет проверки <=25 SQL выполнен. Это не p95
production и не полная задержка с Telegram. К подтверждению кнопки добавляется
один editMessageText с timeout=5 с; дополнительных проверок прав через API нет.
Стоимость одного решения O(1) по числу постов. При росте потока в 10 раз растёт
число обращений Telegram; ограничение — сеть и последовательный polling.

На production безопасно выполнены два EXPLAIN ANALYZE BUFFERS для выбора первых
50 идентификаторов материализованной ленты: READ ONLY, statement_timeout=3s.
Execution Time: 0.423 -> 0.410 мс; pubfeed_feed_rank_idx и feeds_post_pkey
сохранены, добавился feeds_author_pkey с Memoize (26 обращений на 50 строк).
Shared hit blocks: 150 -> 231, reads: 3 -> 0. Разное состояние буферов не позволяет
объявлять ускорение. Полный план с переводами/сериализацией не измерялся;
регрессионные тесты бюджета ленты прошли. Индексы не добавлялись.

Ограничения и выпуск
Нагрузочный staging-тест и работа новой версии на production ещё не проверены.
Нет измерения LCP: UI сайта не менялся. Сеть Telegram остаётся нестабильной.
Сохранение решения не гарантирует мгновенную доставку результата при обрыве.
Telegram-очередь по-прежнему имеет ограниченный срок хранения; постоянного
локального inbox эта правка не вводит. Отдельный сбой доставки первоначального
запроса согласования существующим sendMessage не исправлялся этой правкой.
Нет гарантии установления исторической причины для конкретного поста без аудита.

Выпуск: штатный deploy playbook без миграций; nginx restart; HTTP smoke, Django
check, контроль ошибок и проверка нового подтверждения на согласованном канале.
Не очищать общий кеш или очередь Telegram. Откат — возврат только этих изменений
кода; JSON аудита совместим со старой схемой, опубликованные данные не откатывать
автоматически. Откат также вернёт выявленные дефекты согласования.
