## Маршрут

`api.telegram.org` в контейнерах → внутренний Docker gateway Джино
`172.18.0.1:443` → SSH → пользователь `tambur-telegram` на VPS →
HAProxy на `127.0.0.1:1443` → Telegram:443 по IPv4.
TLS проверяется штатно и завершается на Telegram. Ключ находится только на Джино
в `/etc/tambur-telegram-tunnel/`, не в Git. SSH host key закреплён.
Пользователю VPS запрещены shell, пароль, reverse forwarding и остальные
назначения; PermitOpen разрешает только 127.0.0.1:1443. Ключ допускает соединение только с исходящего IP Джино.
Amnezia не меняется. Новая платная инфраструктура не приобретается.
Первый вариант SSH-forward напрямую к доменному имени зависал на недоступном
IPv6 Telegram (SYN-SENT). HAProxy ограничивает выход IPv4 и обновляет адрес через
DNS; fixed IP Telegram в туннеле не зашит. Конфигурация и эквивалентный Compose
лежат в `deploy/telegram-tunnel/`; на VPS, где нет Compose, контейнер запущен
через `docker run` с теми же параметрами: localhost:1443, restart unless-stopped,
read-only, cap-drop ALL, no-new-privileges, 64 MiB, 0,25 CPU, 32 процесса,
логи 2×5 MiB. Публичного proxy-порта нет.

Systemd unit: `deploy/telegram-tunnel/tambur-telegram-tunnel.service`.
`ServerAliveInterval=15`, `ServerAliveCountMax=3`, перезапуск через 5 секунд.
В deploy/.env: `TELEGRAM_API_RELAY_IP=172.18.0.1`.
При пересоздании Docker-сети проверить адрес gateway и bind в unit.

## Процесс и наблюдаемость

- `TelegramPollingRuntime`: startup/deleteWebhook с сохранением очереди,
  getUpdates ≤100, повторы 2–30 с, сохранение cursor при ошибке. Нет API-вызовов
  для мониторинга в обычном цикле. Ошибка DB очереди согласований не блокирует приём.
- `TelegramUpdateProcessor`: существующая логика согласования и обработки;
  callback прогресса без SQL и пользовательских данных.
- `PollingStatus`/`JsonStatusFile`: атомарный маленький JSON в общем volume.
  Прогресс внутри большого пакета пишет файл не чаще раза в 5 секунд.
- `PollingHealth`: потеря API, отсутствие heartbeat, зависшая обработка и
  исключения из очереди согласований дольше 120 секунд делают процесс unhealthy.
- `TelegramWatchdog`: отдельный контейнер проверяет файл каждые 15 секунд,
  отправляет в email и MAX независимо, повторяет неудачную отправку раз в минуту,
  доставленное предупреждение — раз в час. После успешного цикла сообщает о
  восстановлении. Перезапуск процесса без успешного цикла восстановлением не считается.
  Состояние доставки сохраняется в volume, поэтому обычный restart не дублирует тревогу.
- `telegram-bot` запускается отдельно от gunicorn; web polling выключен.
  Docker перезапускает завершившийся процесс. Unhealthy сам по себе Docker
  не перезапускает: watchdog предупреждает, избегая бесконечных рестартов
  из-за сетевого сбоя или одного проблемного поста.

Настройка на сервере (значения получателей только в deploy/.env.backend):
`TELEGRAM_ALERT_EMAIL`, `TELEGRAM_ALERT_MAX_CHAT_ID`.
В deploy/.env добавить профиль `COMPOSE_PROFILES=telegram-watchdog`, сохранив
другие профили. Watchdog отказывается стартовать без обоих адресатов.
SMTP timeout 10 с, MAX 20 с. Период обнаружения около 2 минут плюс до 15 секунд
опроса и время отправки. При сбое одного транспорта второй продолжает работать.

## Стоимость и проверка

Никаких новых таблиц, индексов, кешей и обхода всех постов. Healthcheck не делает
SQL/HTTP. Ресурс мониторинга постоянный; пакет обновлений остаётся ≤100.
При росте входящего потока в 10 раз растёт существующий последовательный импорт,
а не число проверок статуса. Ограничение — скорость обработки медиа и внешних API;
для большей нагрузки нужен отдельный durable inbox, а не рост лимита getUpdates.

Локально: полный набор 127 тестов Telegram прошёл после выделения runtime;
добавлена проверка, запрещающая ложное восстановление при restart (всего 128).
Тесты используют отдельную локальную PostgreSQL и текущую схему моделей без
исторических миграций: на пустой БД старые миграции падают. Это не проверка миграций.
`manage.py check`, frontend build и diff check также проверяются перед выпуском.

Микрозамер `tests/benchmark_telegram_runtime.py`: 100 повторов, 10 пакетов по
100 событий, обработчики/HTTP/DB заменены заглушками, реальная запись status-файла.
Медиана старого цикла 0,383 мс, нового 5,790 мс на 1000 заглушечных событий
(добавление около 0,0054 мс/событие). Это цена наблюдаемости, не ускорение импорта
и не production p95. Запуск из корня: `.venv/bin/python tests/benchmark_telegram_runtime.py`.
Baseline читается из commit `7b38312`, а не из меняющегося HEAD.

Безопасная prod-проверка до переключения: прямой Telegram — timeout 5–8 с;
через SSH getMe 269 мс, getWebhookInfo 252 мс; ожидало 146 обновлений.
getUpdates диагностикой не вызывается, чтобы не конкурировать с получателем.
Нагрузочные тесты и очистка общего кеша на проде не выполнялись.

## Ограничения и откат

Это контроль связи и обработки входящих событий, а не гарантия доставки каждого
отдельного исходящего сообщения. Исчерпанные попытки отправки согласований
по-прежнему требуют отдельного разбора durable-очереди в админке.
Один ошибочный импорт может удерживать cursor; теперь это обнаруживается.
Telegram хранит ожидающие обновления ограниченное время (до 24 часов), поэтому
долгий прошлый сбой нельзя автоматически объявить восстановленным без сверки постов.

При полном падении Джино watchdog на том же сервере тоже недоступен; для такого
случая нужен внешний монитор доступности сервера. Отказ VPS или изменение gateway
теперь обнаруживаются как потеря связи с Telegram, но требуют ремонта маршрута.

Откат приложения: вернуть предыдущий commit, остановить telegram-bot/watchdog,
включить один web polling и сохранить работающий tunnel/extra_hosts. Нельзя
одновременно включать два получателя. Возвращать прямой адрес Telegram допустимо
только после успешной проверки прямого TLS с Джино. Очередь не очищать.
