# Проверка Telegram 2026-10-15

Production HEAD: 91fe1e4, рабочее дерево сервера чистое. Диагностика была
только чтением: без getUpdates, сброса очереди, перезапуска, отправки сообщений
или изменения привязок. Конкретный канал жалобы ещё не указан.

## Подтверждённые наблюдения

- В ограниченном окне журнала backend (последние 3000 строк за 6 часов)
  найдены 24 события `cursor retained`, тип ошибки — TelegramAccessCheckUnavailable.
  Polling включён; необработанный update задерживает дальнейшую последовательную
  обработку. Ожидание повторной попытки не означает сохранность всех старых постов.
- Первые getMe и getWebhookInfo из контейнера завершились URLError примерно
  через 7 секунд. Позднее два getMe успешно вернули идентичность comuna_tg_bot
  за 171.0 и 148.6 мс; следующий getWebhookInfo — тайм-аут за 6006 мс.
  Размер очереди получить не удалось. Прокси-переменные не настроены.
- В контейнере API закреплён за 149.154.167.220. DNS хоста в момент проверки
  вернул 149.154.166.110. Ограниченные TCP/TLS-пробы с проверкой сертификата:
  оба IP с хоста — тайм-аут; из контейнера .220 один раз ответил HTTP 302
  за 244 мс, .110 — тайм-аут. Удаление закреплённого адреса не обосновано этими
  измерениями. Не установлено, на каком участке сети теряются соединения.
- В старом коде приватной пересылки `_is_bot_admin` возвращает False не только
  при отсутствии прав, но и при None после сетевой ошибки getMe/getChatMember.
  Поэтому сообщение «Бот не является админом» недостоверно при таком сбое.

Telegram хранит входящие обновления не больше 24 часов:
https://core.telegram.org/bots/api#getting-updates . Поэтому после восстановления
соединения нужна сверка пропущенных публикаций конкретного канала, а не обещание,
что вся очередь обязательно догонится. Права канала без его ссылки не проверены.

## Подготовленное исправление

Существующий TelegramChannelAccessVerifier — единый объект проверки для импорта
и приватной пересылки; `_is_bot_admin` остаётся тонким адаптером. Нестабильная
сеть, недоступная идентичность и временные API-ошибки дают отдельное исключение.
Приватный обработчик сообщает о временном сбое и предлагает повторить пересылку,
не меняя привязку и не публикуя пост без проверки. При подтверждённом отказе
сообщение предлагает проверить именно comuna_tg_bot. Проверка не требует права
публикации в Telegram для чтения канала. Импорт сохраняет прежнюю семантику
повтора неуспешного обновления. Ошибки идентификации не раскрывают токен.

Исправление не устраняет сетевую недоступность. Следующий эксплуатационный шаг —
проверить маршрут исходящих соединений к Telegram у провайдера/на сервере;
если он нестабилен постоянно, выбрать проверенный маршрут исходящего трафика.
Произвольные публичные прокси и отключение TLS-проверки не используются.

## Проверки и стоимость

33 локальных теста прошли (права, тайм-ауты, HTTP 429/503, связывание сообщества,
успешная пересылка, защита от дублей, альбомы и повтор импорта). Django check
и diff --check успешны. Отказы приватной пересылки проверены SimpleTestCase:
нет обращений к БД, публикаций и дополнительных проверок Telegram.

Микрозамер одного адаптера: одинаковые ответы API в памяти, бот уже известен,
200 последовательных вызовов на сценарий; это CPU-overhead, не end-to-end latency.

| Сценарий | Медиана до → после, мс | Вызовов API до → после |
|---|---|---|
| Администратор | 0.0024 → 0.0066 | 1 → 1 |
| Удалён из канала | 0.0024 → 0.0065 | 1 → 1 |
| Тайм-аут | 0.0003 → 0.0044 | 1 → 1 |

Тайм-аут сетевой проверки остаётся 5 секунд; новые повторы/кеши/таблицы не добавлены.
При неизвестной идентичности дополнительно нужен существующий getMe. Стоимость
одной проверки O(1), при росте потока в 10 раз растёт число вызовов Telegram;
последовательный polling остаётся ограничением. Миграций нет, откат — возврат кода.
Staging-нагрузка, восстановление связи и production-проверка новой реализации
ещё не выполнены; новая версия не выложена.
