# Контракт продуктовых метрик Тамбура

## Источники

- Яндекс Метрика: счётчик `106046128`, только read-only OAuth (`metrika:read`).
- Production backend Тамбура через read-only Analytics API: Django ORM агрегирует `SiteUserProfile`, `Post`, `PostComment`, `PostLike`, `PostCommentLike`, `PostPollVote`, `PostRatingVote`, `PostRead`, `PostFavorite`, `ComunSubscriptionEvent`, `PostDailyView`. Локальную БД проекта не использовать. Ключ ограничен scope, сроком действия, списком сообществ и при необходимости IP.
- Отчёты: `backend/var/product-analytics/<конец-недели>.json`.
- PDF: `output/pdf/tambur-weekly-<конец-недели>.pdf`.
- Backlog Notion: data source `collection://321e9888-3764-809a-8c7d-000b7c6f6956`, родительская страница «Тамбур».
- Git log: вспомогательный журнал кандидатов на продуктовые изменения, не журнал деплоев.

## North Star

Отчёт показывает две совместимые части North Star:

- `Weekly Valuable Users` из Метрики охватывает анонимные и авторизованные клиентские действия, включая meaningful read;
- `Authenticated Weekly Value Users` из production backend — уникальные авторизованные пользователи с комментарием, лайком, голосом, отметкой прочтения, избранным или подпиской.

Не складывай эти значения: аудитории пересекаются. Используй production backend как точный источник серверных действий, а Метрику — для анонимного чтения и контекста трафика.

Ценностные действия:

- `signup_completed` — завершена регистрация;
- `meaningful_read` — активный просмотр поста не менее 60 секунд и прокрутка не менее 70%;
- `community_subscribed` — подписка на сообщество;
- `comment_created` — создан комментарий или ответ;
- `vote_created` — отправлен голос в рейтинге или опросе;
- `post_published` — опубликован пост.

Guardrail: `community_unsubscribed` отслеживается отдельно и не входит в North Star.

Если цель `valuable_action` отсутствует, поле North Star имеет `status = proxy`. `proxy_non_bounce_users` можно использовать только как временный directional proxy и нельзя называть Weekly Valuable Users.

Регистрация сама по себе не является ценностным действием. Отдельно считай долю новых зарегистрированных пользователей, совершивших серверное ценностное действие в ту же неделю (`same_week_activation_rate`). Если production API недоступен или несвеж, не считай нули фактом отсутствия активности.

## Диагностические метрики

Пользователи, визиты, просмотры страниц, доля новых посетителей, отказы, глубина просмотра, средняя длительность визита; разрезы по источнику трафика, типу устройства и стартовой странице. Основной отчёт использует фильтр `ym:s:isRobot=='No'`; отдельный блок `traffic_quality` показывает объём распознанного роботного трафика.

Основные сравнения:

- week-over-week: последняя завершённая неделя против предыдущей;
- устойчивый baseline: медиана четырёх недель до анализируемой.
- влияние релиза: минимум две полные недели до и после предполагаемой даты релиза, без релизной недели; для свежей фичи явно указывать, если post-период короче.

Описывай абсолютные значения и относительное изменение вместе. При малых объёмах понижай confidence и не делай сильных выводов.

## Два контура продуктовых решений

1. `product_hypotheses`: какие новые возможности проверить. Продуктовая гипотеза содержит аудиторию, изменение пользовательского опыта, ожидаемое поведение и критерий успеха. Настройка аналитики, целей, событий, ETL или дашборда сюда не входит.
2. `existing_feature_decisions`: что делать с уже выпущенными фичами. Допустимые решения: `оставить`, `изменить`, `кандидат на удаление`, `недостаточно данных`.
3. `measurement_tasks`: отдельный технический backlog пробелов измерения. Эти задачи не входят в лимит продуктовых гипотез.

Для существующей фичи обязательно фиксировать дату и источник релиза, pre/post окна, метрики, альтернативные объяснения и confidence. Сравнение до/после имеет уровень причинности `корреляция`. Решение об удалении требует feature-level adoption/event и эксперимента с отключением либо устойчивого вреда; агрегатные метрики сайта сами по себе недостаточны.

## Backlog Notion

Создавай только предложения. Обязательные свойства:

- `Name`: конкретная проверяемая гипотеза;
- `Status`: `Сделать`;
- `Status 1`: `Предложения`;
- `Приоритет`: `Важно`, `Терпит` или `Потом`;
- `Направление`: наиболее подходящее из `Привлечение авторов`, `Качество контента`, `Контент фичи`, `Ошибки`, `Развитие проекта`, `Новые фичи`;
- `Платформа`: заполняй только если эффект явно платформенный.

Перед созданием запроси активные и архивные строки. Дубликат — карточка с той же пользовательской проблемой и близким решением для того же сегмента. Вместо дубля упомяни существующую карточку в отчёте.

Название задачи начинается с одного из маркеров: `[Новая фича]`, `[Изменить]`, `[Изменить/удалить]`, `[Измерение]`. Для решения `оставить` карточка не создаётся, если не требуется отдельное действие.

В теле новой карточки фиксируй:

1. Evidence: период, metric, baseline, current, delta, затронутый сегмент.
2. Hypothesis: «Если …, то …, потому что …».
3. Experiment: изменение, аудитория, длительность/условие остановки.
4. Success: основная метрика и минимально значимый эффект.
5. Guardrails: отказы, отписки или другая релевантная метрика.
6. Scoring: impact, effort, confidence с кратким обоснованием.
7. Causality: `наблюдение`, `корреляция` или `подтверждено экспериментом`.

## Итог анализа для PDF

Сохраняй UTF-8 JSON со следующими полями:

- `executive_summary`: главный вывод одним абзацем;
- `observations`: массив ключевых наблюдений;
- `product_hypotheses`: массив объектов `title`, `url`, `audience`, `product_change`, `target_behavior`, `rationale`, `success_metric`, `priority`, `confidence`;
- `measurement_tasks`: массив объектов `title`, `url`, `rationale`, `priority`;
- `new_feature_decisions`: устаревающий alias для `product_hypotheses`, допустимый для обратной совместимости;
- `existing_feature_decisions`: массив объектов `feature`, `release_date`, `evidence`, `pre_period`, `post_period`, `metric_changes`, `decision`, `rationale`, `confidence`, `task_title`, `task_url`;
- `hypotheses`: устаревающий alias для `new_feature_decisions`, допустимый для обратной совместимости;
- `existing_related`: массив объектов `title`, `url`, `reason` для найденных дублей;
- `next_steps`: массив конкретных следующих действий.
