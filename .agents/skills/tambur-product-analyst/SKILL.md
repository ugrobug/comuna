# Еженедельный продуктовый аналитик Тамбура

Сначала прочитай [контракт метрик и backlog](references/metric-contract.md).

1. Из корня проекта запусти `.venv/bin/python backend/manage.py tambur_product_report --stdout`. Отчёт объединяет Метрику и серверные события, которые команда получает через read-only Analytics API production. Токен бери только из `TAMBUR_ANALYTICS_API_TOKEN_FILE`; не печатай его и не включай в отчёты. Никогда не используй локальную БД проекта для еженедельного анализа. Анализируй только последнюю полностью завершённую неделю. Если `internal_product.status != fresh`, не интерпретируй нули и явно укажи, что production API недоступен или источник несвеж. Если Метрика или оба источника продуктовых действий недоступны, не записывай гипотезы в Notion.
2. Сравни трафик и продуктовую активность с предыдущей неделей, медианой четырёх предшествующих недель и историческим недельным рядом. Метрика отвечает за привлечение и поведение сессий; production backend — за регистрации, активированных новичков, авторизованных value users, публикации, комментарии, лайки, голосования, отметки прочтения, избранное и подписки/отписки. При необходимости запроси разрешённые сообщества через `/api/agent/v1/analytics/communities/` и их 30-дневные ряды через detail endpoint. Найди вклад источников, устройств и посадочных страниц. Не приписывай причинность корреляции.
3. Запроси существующие строки backlog в Notion и исключи дубли по проблеме, аудитории и предлагаемому изменению. Прочитай завершённые задачи и их описания, чтобы связать релизы с последующим изменением метрик. Git-коммиты из отчёта считай только кандидатами на изменения: дата коммита не подтверждает production-деплой.
4. Проведи два независимых контура решений:
   - **новые фичи** — сформируй не более трёх продуктовых гипотез с наиболее сильными данными. Продуктовая гипотеза обязана менять опыт конкретной аудитории и целевое поведение; настройка целей, событий, отчётов или дашбордов продуктовой гипотезой не считается;
   - **существующие фичи** — выбери недавно выпущенные и одну-две фичи из ротации, сравни полные недели до/после релиза без релизной недели и присвой решение `оставить`, `изменить`, `кандидат на удаление` или `недостаточно данных`.
5. Не называй сравнение до/после доказанным влиянием без контрольной группы. `Кандидат на удаление` допустим только при наличии feature-level сигнала использования и устойчивого отсутствия ценности/вреда; иначе создай задачу на измерение или A/B-отключение.
6. Для новых фич и действий над существующими фичами создай/обнови задачи в Notion. Новые предложения: `Status = Сделать`, `Status 1 = Предложения`. Используй префиксы `[Новая фича]`, `[Изменить]`, `[Изменить/удалить]`. Задачи на данные записывай отдельно с префиксом `[Измерение]`; они не входят в лимит продуктовых гипотез и не подменяют их. Решение `оставить` фиксируй в отчёте без отдельной задачи, если follow-up не нужен. В задаче укажи evidence, pre/post, метрику фичи, эксперимент, success, guardrails, confidence и уровень причинности.
7. После работы с backlog запиши итог анализа по схеме из контракта в `backend/var/product-analytics/<конец-недели>-analysis.json`. Создай PDF командой `.venv/bin/python backend/manage.py tambur_product_pdf --report backend/var/product-analytics/<конец-недели>.json --analysis backend/var/product-analytics/<конец-недели>-analysis.json`. PDF обязан содержать отдельные разделы «Внутренняя продуктовая активность», «Ревизия существующих фич», «Продуктовые гипотезы» и «Задачи измерения». Проверь PDF рендерингом всех страниц и приложи PDF к итоговому сообщению.

Никогда не меняй продуктовый код, статусы рабочих задач и production в рамках недельного анализа. Итогом дай короткий отчёт: движение North Star, главные драйверы, решения по существующим фичам, новые гипотезы, созданные/обновлённые задачи, пробелы в измерении и ссылку на PDF.
