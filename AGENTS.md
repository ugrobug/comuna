# AGENTS.md

## Обязательная архитектура: ООП, экономичность и масштабирование

- Весь новый и существенно перерабатываемый прикладной код разрабатывать в парадигме ООП. Выделять классы с понятной ответственностью, инкапсулировать состояние и бизнес-правила, задавать явные контракты взаимодействия. Применять SOLID соразмерно задаче; предпочитать композицию глубокой иерархии наследования.
- HTTP views, обработчики ботов, фоновые задачи и UI-компоненты должны быть тонкими точками входа: принимать данные, вызывать методы прикладных объектов и возвращать результат. Бизнес-логику не накапливать в обработчиках, компонентах или общих модулях с несвязанными функциями. Функции и hooks, требуемые фреймворком, использовать как адаптеры к объектам; SQL, конфигурацию и шаблоны оставлять в формате соответствующего инструмента.
- Зависимости классов задавать явно, передавать через конструктор или аргументы методов. Границы интеграций оформлять интерфейсами/протоколами и адаптерами там, где это позволяет тестировать или заменять реализацию. Не вводить скрытое глобальное состояние, классы с несвязанными обязанностями и обёртки, которые только переименовывают функцию без ответственности.
- Архитектурные паттерны выбирать до реализации исходя из сценария и стоимости: прикладной сервис для операции, отдельный объект чтения для сложной выборки, стратегия для вариантов поведения, адаптер для внешней системы. Не создавать все эти слои автоматически; каждый должен решать конкретную задачу. Использовать существующие объекты и пакетные операции проекта вместо дублирования логики.
- Сразу проектировать экономное масштабируемое решение: определить ожидаемый объём данных, частоту и параллельность операций, бюджет задержки и стоимость одной операции по CPU, памяти, запросам БД, диску, сетевому трафику и платным API. Отдельно учитывать постоянные расходы инфраструктуры и сопровождения. Предпочитать самый простой вариант, который выполняет эти требования и допускает дальнейшее расширение.
- Описывать поведение при росте данных и нагрузки, например в 10 раз: какая работа растёт, где её предел и какой ресурс станет ограничением. Ограничивать размер страниц/пакетов, память, параллельные задачи, время ожидания и число повторов. Не загружать неограниченные коллекции и не создавать неограниченную очередь задач или сетевых вызовов внутри запроса.
- Границы состояния, транзакций и обработки событий проектировать так, чтобы можно было безопасно добавить workers: идемпотентность повторов, согласованность данных, управляемая конкуренция и наблюдаемое отставание. Подготовленные данные обновлять инкрементально там, где это экономнее полного пересчёта; предусматривать сверку и восстановление.
- Расширение сервера, новый кеш, брокер, сервис или смену стека оценивать вместе с дополнительными расходами и сложностью эксплуатации. Указывать измеренный выигрыш либо проверяемую гипотезу, альтернативы и условия, при которых масштабирование действительно потребуется. Не перекладывать неэффективный алгоритм на более дорогую инфраструктуру.
- Существенные архитектурные решения кратко фиксировать в документации изменения: ответственность классов, движение данных, паттерн и причина выбора, оценка роста, стоимость, ограничения, способ проверки и отката. Изменять затронутую область последовательно, сохраняя API; не затевать несвязанный полный рефакторинг существующего кода.

## Обязательные правила производительности

Применять при изменениях поведения приложения: API чтения и записи, лент, каталогов, поиска, фильтров, SQL/ORM, сериализаторов, кешей, загрузки страниц, ботов, интеграций и фоновых задач. После внедрения изменений проверка быстродействия обязательна; её объём выбирать по затронутому сценарию и риску. Для правок только текста или документации без изменения поведения нагрузочные проверки не требуются; для правок оформления проверять отображение, а при влиянии на отрисовку — также скорость интерфейса.

Основание: в сентябре 2026 лента сообщества выполняла 150 SQL-вызовов и отвечала 18–24 секунды при промахе кеша. Главной потерей был COUNT поверх DISTINCT полных строк после JOIN переводов. После изменения выборки и отделения счётчиков карточки отдавались за 218–240 мс при 18 SQL-вызовах. Это отдельные серверные замеры, не p95 всей страницы. Разбор реализации: [docs/community-feed-performance.md](docs/community-feed-performance.md).

### 1. Сначала определить стоимость чтения

- До реализации описать, какие данные нужны первому экрану, какие таблицы участвуют, как ограничивается результат и что произойдёт при росте числа постов, переводов и пользователей.
- При изменении существующего пути снять исходные время ответа, число SQL-вызовов и время SQL. Использовать имеющиеся `Server-Timing`, nginx timing/cache status и `CaptureQueriesContext`, а не только субъективное «быстро открылось».
- Проверять промах кеша ответа и авторизованный путь отдельно от попадания в кеш. Прогретый ответ не доказывает, что запрос к данным эффективен.
- Для обычной первой страницы ленты ориентир: серверный p95 без кеша ответа ≤500 мс, бюджет ≤30 SQL-вызовов на 10 карточек. С ростом страницы с 10 до 30 карточек число запросов настроек и связанных объектов не должно расти пропорционально числу карточек.
- Это бюджет проектирования, а не универсальная гарантия для любого endpoint. Для обоснованного исключения указать стоимость, причину и способ ограничения работы в описании изменения. Не объявлять несколько быстрых запросов подтверждённым p95; указывать объём данных, число измерений, нагрузку и состояние кеша.

### 2. Ограничивать работу базы до загрузки больших данных

- Не использовать `DISTINCT` как автоматическое исправление дублей от JOIN. Сначала понять кратность связи; для проверки наличия связанного объекта рассмотреть `EXISTS`. Выбирать вариант по плану и замерам, а не считать EXISTS всегда быстрее.
- Не считать количество через DISTINCT полных строк с текстом/JSON. Для подходящих queryset считать уникальные идентификаторы без ненужного ORDER BY; проверять фактически сгенерированный SQL.
- В сложной ленте сначала выбирать ограниченную страницу идентификаторов, затем загружать содержимое и связи только этой страницы. Не сортировать и не сериализовать весь набор постов ради первых десяти карточек.
- Сортировка пагинации должна иметь уникальный завершающий ключ, например `created_at, id`. Для новой глубокой или бесконечной прокрутки предпочитать курсор; сохранение OFFSET в существующем API не отменяет проверки глубокой страницы.
- При двухэтапной выборке повторно проверять видимость и доступ при загрузке карточек: между запросами пост может быть скрыт или приглашение может получить подтверждённого спутника.
- Не обходить всю ленту в Python ради фильтра, рейтинга или счётчика на каждый HTTP-запрос. Для часто используемого вычисляемого признака рассмотреть индексируемое поле или подготовленную таблицу с понятным обновлением.
- Частые связи и фильтры моделировать явными полями/FK/таблицами связей. JSON использовать для гибких исходных данных; фильтрация по нему в критическом пути требует подходящего индекса и проверенного плана.

### 3. Проверять соответствие индексов запросу

- При добавлении источника, языка, статуса, ветки OR, фильтра или нового порядка сортировки повторно проверить индексы потребителя. Наличие индекса с похожим именем недостаточно.
- Для частичного индекса проверить, что WHERE запроса подразумевает предикат индекса. Например, индекс только для `source = manual_comun` не покрывает ветку `source IN (manual_comun, max)` целиком.
- Сопоставлять реальные выражения SQL, порядок колонок, условия и сортировку с определением индекса. Для существенного изменения критического запроса изучить EXPLAIN; на репрезентативных данных использовать EXPLAIN ANALYZE BUFFERS с ограничением времени.
- Небольшой последовательный проход допустим; цель — ограниченная стоимость запроса, а не использование индекса любой ценой. Не добавлять индексы на все поля и не удалять индекс только из-за разового `idx_scan = 0`.
- Индексы больших рабочих таблиц создавать способом, не блокирующим обычную запись, например CONCURRENTLY в неатомарной миграции. Проверять успешное применение, `indisvalid` и `indisready`; предусматривать откат. Рост стоимости записи и размера индексов учитывать.

### 4. Не допускать запросов на каждую карточку

- Не выполнять SQL или внешние HTTP-вызовы в цикле сериализации карточек. Данные авторов, сообществ, голосов, избранного, рейтингов и связей загружать пакетно.
- Передавать уже загруженные объекты и настройки явно либо использовать контекст одного чтения. Настройки шаблонов и рейтинга не загружать повторно для каждого поста и каждой проверки типа.
- Проверять, что код действительно использует prefetch. Последующие `.filter()`/`.order_by()` связанного менеджера могут выполнить новый запрос; использовать точно настроенный Prefetch/to_attr или подготовленные коллекции.
- Кеш внутри запроса должен завершаться вместе с ним, очищаться при ошибке и быть изолирован между конкурентными запросами. Не использовать глобальный изменяемый словарь для пользовательских данных и не переносить снимок чтения в обработчики записи.
- Для исправленного N+1 добавить тест с несколькими различными авторами/сообществами и бюджетом запросов. Один автор на всех карточках или мок сериализатора могут скрыть проблему.

### 5. Первый экран не должен ждать необязательную работу

- Полные счётчики, статистику и тяжёлые дополнительные блоки загружать отдельно, если они не нужны для отображения карточек. Для `has_more` использовать `limit + 1`, не COUNT всей ленты.
- Отделять DTO чтения карточки от данных редактора. Не отправлять одинаковые настройки и описание сообщества в нескольких ответах без необходимости.
- Независимые запросы выполнять параллельно; не добавлять `await parent()` или другую последовательную зависимость без потребности в её результате. Авторизацию, от которой зависит доступ, обходить нельзя.
- При смене фильтра, языка или страницы отменять/игнорировать устаревшие асинхронные ответы. Ошибка или ожидание счётчика не должны выглядеть как достоверный ноль и не должны ломать пагинацию.
- Тяжёлые редакторы, карты и редкие интерактивные компоненты загружать по необходимости. Проверять состав и размер начального JS/CSS, а не только успешность сборки.
- Изображения отдавать в размерах, соответствующих отображению и DPR, с заданными габаритами. Изображение первого экрана, определяющее LCP, не откладывать через lazy loading; остальные загружать по потребности. Не подключать внешнюю интеграцию с пустым/undefined ID.
- Сохранять совместимость API с web и мобильным приложением: новые компактные ответы вводить через явный режим или версию, пока остальные потребители не переведены.

### 6. Кеш и фоновые задачи проектировать явно

- Сначала сделать ограниченным и измеримым путь без кеша. Не закрывать многосекундный запрос одним увеличением TTL, числом workers или мощностью сервера.
- Для каждого нового кеша определить ключ, разделение по пользователю/языку/фильтрам, TTL, события сброса и поведение при одновременных промахах.
- Инвалидация должна работать между всеми workers, фоновыми задачами и слоями кеша. LocMemCache не является общим кешем; смена версии кеша приложения не очищает HTML/API, сохранённые в nginx/CDN.
- Общий кеш публичных данных отделять от персональных признаков. Сохранять актуальную проверку доступа, `private/no-store` и правила исчезновения скрытого контента. Проверять публикацию, изменение, удаление и смену доступа при прогретом кеше.
- Импорт, переводы, массовый пересчёт и генерацию тяжёлых материалов выполнять в фоне. Задачи должны допускать безопасный повтор, иметь ограниченные пакеты и наблюдаемое отставание; GET страницы не должен запускать полный пересчёт.
- Новую инфраструктуру, подготовленные таблицы и смену стека обосновывать измеренным узким местом. Переписывание Python не устраняет время выполнения того же SQL. Не вводить Redis, брокер или микросервисы автоматически для каждой задачи.

### 7. Обязательное тестирование быстродействия после изменений

- После каждого изменения поведения повторять замеры затронутого сценария на новой реализации, даже если задача не называлась оптимизацией. Успешная сборка, unit-тесты и HTTP 200 не заменяют проверку скорости.
- Минимум — воспроизводимый сценарий до/после на сопоставимых данных с зафиксированным окружением, результатами и проверкой корректности. Для новой функции заранее определить бюджет и проверить его; сравнение с несуществующей старой версией не придумывать.
- Для изменений алгоритма, модели данных, кеширования или параллельной обработки дополнительно проверять репрезентативный объём, рост данных и конкурентную нагрузку на staging. Оценивать задержку и пропускную способность вместе с CPU, памятью, БД, очередями и внешними вызовами; ускорение ценой неограниченного роста ресурсов не считать успешным.
- После деплоя повторять безопасные контрольные замеры и проверять доступные метрики реальных запросов, ошибок и ресурсов. Нагрузочный тест на production без отдельной договорённости не проводить. Не подменять результат работающей версии локальным экспериментом.
- Новую подтверждённую регрессию или нарушение согласованного бюджета устранять до выпуска. Если она обнаружилась после выпуска, проверить причину и применить исправление либо безопасный откат по плану релиза. Не объявлять такую работу завершённой только потому, что функциональность работает; ограничения среды и недоказанные показатели явно отражать в результате.

Перед объявлением работы завершённой:

1. Сравнить до/после на одинаковом наборе данных и сценарии: время, SQL-вызовы, время БД, объём ответа; отдельно отметить HIT/MISS, гостя/авторизованного пользователя и включённые/отложенные части ответа.
2. Проверить корректность состава и порядка выдачи, переводов, категорий, всех затронутых источников, прав доступа, отложенных/скрытых постов, границ страниц и смены видимости между запросами.
3. Для изменений SQL/сериализации добавить содержательные регрессионные проверки количества запросов и результатов. Не фиксировать хрупкий миллисекундный порог в обычном unit-тесте; время измерять отдельно на репрезентативном окружении.
4. Подтвердить скорость первого экрана отдельно от скорости API, если менялась загрузка страницы. Серверный TTFB не выдавать за LCP/INP пользователя; несколько наблюдений не выдавать за нагрузочный тест.
5. В описании результата указать измерения, ограничения проверки и оставшиеся потери. Если нужные данные или окружение недоступны, явно назвать непроверенную часть; не заявлять достигнутый бюджет без подтверждения.

На production не проводить нагрузочный тест и не очищать общий кеш ради замера без отдельной договорённости. Диагностику ограничивать небольшим числом чтений, read-only транзакцией и timeout; EXPLAIN ANALYZE действительно выполняет запрос. Не записывать в отчёты и логи SQL-параметры, токены и пользовательский контент. Для широких испытаний использовать staging.

## Deploy Playbook

Используй этот порядок для любого деплоя в прод.

### 1. Локальная проверка перед релизом

Из корня репозитория:

```bash
npm run build
.venv/bin/python backend/manage.py check
git status --short
```

Правила:

- Не деплой, если `npm run build` или `manage.py check` падают.
- Не тащи в релиз неожиданные локальные файлы.
- Если есть незакоммиченные пользовательские изменения, сначала явно понять, входят ли они в релиз.

### 2. Коммит и push

```bash
git add <нужные_файлы>
git commit -m "<message>"
git push origin main
git rev-parse --short HEAD
```

### 3. Прод-сервер

Прод-код лежит здесь:

- `/opt/comuna/app`

Compose-файлы и env лежат здесь:

- `/opt/comuna/app/deploy/docker-compose.prod.yml`
- `/opt/comuna/app/deploy/.env`

Важно:

- Не использовать `/opt/comuna/app/.env` — это неправильный путь.
- Для backend-контейнера внутри Docker использовать `python manage.py ...`, а не `.venv/bin/python backend/manage.py ...`.

### 4. Базовый деплой

Если миграций нет:

```bash
ssh <prod> 'cd /opt/comuna/app && git pull && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env up -d --build && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env restart nginx'
```

### 5. Деплой с миграциями

Если в релизе есть новые Django migration-файлы:

```bash
ssh <prod> 'cd /opt/comuna/app && git pull && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env up -d --build && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env exec -T backend python manage.py migrate && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env restart nginx'
```

Если нужно прогнать миграции отдельно после уже выполненного `up -d --build`:

```bash
ssh <prod> 'cd /opt/comuna/app && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env exec -T backend python manage.py migrate'
```

После любого `up -d --build` обязательно перезапустить nginx:

```bash
ssh <prod> 'cd /opt/comuna/app && docker compose -f /opt/comuna/app/deploy/docker-compose.prod.yml --env-file /opt/comuna/app/deploy/.env restart nginx'
```

Причина: при пересоздании `backend` или `frontend` Docker может выдать контейнеру новый IP, а живой nginx продолжит некоторое время ходить в старый upstream и отдавать `502 connect() failed`. Рестарт nginx обновляет upstream-адреса сразу.

### 6. Проверка после деплоя

Проверять лучше через локальный nginx на сервере, а не внешним `curl`, потому что внешний DNS иногда шумит.

Главная:

```bash
ssh <prod> "curl -sS -I -H 'Host: tambur.pub' http://127.0.0.1/ | head -n 10"
```

Страница существующего поста:

```bash
ssh <prod> "curl -sS -I -H 'Host: tambur.pub' http://127.0.0.1/b/post/4492-bred-ili-geniy-retsenziya-na-film-druzhba-2024 | head -n 10"
```

Ожидаемый результат:

- `HTTP/1.1 200 OK`

Дополнительно полезно проверить текущий коммит на сервере:

```bash
ssh <prod> 'cd /opt/comuna/app && git rev-parse --short HEAD'
```

Для изменений поведения после деплоя также повторить безопасный сценарий быстродействия из раздела «Обязательное тестирование быстродействия после изменений», сравнить с исходными замерами и проверить ошибки и потребление ресурсов. Для подтверждения p95 использовать достаточную выборку метрик; несколько smoke-запросов обозначать как отдельные наблюдения.

### 7. Что считать успешным деплоем

Деплой завершен только если выполнены все условия:

- `git push` успешен
- `git pull` на сервере успешен
- `docker compose ... up -d --build` завершен без ошибок
- если есть миграции, `python manage.py migrate` завершен без ошибок
- `docker compose ... restart nginx` завершен без ошибок
- главная и хотя бы одна реальная страница поста отвечают `200`
- API endpoint, например `/api/special-projects/book/status/`, отвечает `200`
- для изменений поведения выполнена проверка быстродействия работающей версии; нет новой подтверждённой регрессии, нарушающей согласованный бюджет, а ограничения измерений зафиксированы

### 8. Частые ошибки

#### Неправильный env file

Неправильно:

```bash
--env-file /opt/comuna/app/.env
```

Правильно:

```bash
--env-file /opt/comuna/app/deploy/.env
```

#### Неправильный путь к Python внутри backend-контейнера

Неправильно:

```bash
python backend/manage.py migrate
.venv/bin/python backend/manage.py migrate
```

Правильно:

```bash
python manage.py migrate
```

#### Серверные env-файлы пачкают `git status`

На проде рабочими могут быть файлы:

- `/opt/comuna/app/deploy/.env.backend`
- `/opt/comuna/app/deploy/.env.frontend`

Они не должны мешать `git pull`.

Правильное поведение:

- Не коммитить их в репозиторий.
- Не удалять их в ходе обычного деплоя.
- На сервере держать их в `.git/info/exclude`, чтобы `git status` оставался чистым:

```bash
cd /opt/comuna/app
echo 'deploy/.env.backend' >> .git/info/exclude
echo 'deploy/.env.frontend' >> .git/info/exclude
```

#### На проде остались старые stash

Если `git pull` на проде блокируется из-за локальных изменений:

- Сначала посмотреть `git status --short`.
- Если это временные серверные правки, перед деплоем сохранить их в `git stash`.
- Если stash уже устарел и изменения есть в `main`, сначала сохранить patch-бэкап, потом удалить stash.

Безопасный шаблон:

```bash
cd /opt/comuna/app
mkdir -p deploy/git-cleanup-backups
git stash show -p stash@{0} > deploy/git-cleanup-backups/stash0.patch
git stash drop stash@{0}
```

Папку с backup patch-файлами тоже нужно держать в `.git/info/exclude`:

```bash
echo 'deploy/git-cleanup-backups/' >> .git/info/exclude
```

### 9. Поведение агента

- Если пользователь просит `деплой`, делать полный цикл, а не останавливаться на коммите.
- Если в процессе найден неожиданный мусор в рабочем дереве, остановиться и спросить пользователя.
- Если прод блокируется из-за локальных серверных файлов, сначала отделить рабочие env/stash от кода и только потом делать `git pull`.
- Если серверная команда упала из-за неверного пути, исправить и продолжить, а не завершать задачу частично.
- В финальном ответе всегда писать:
  - commit hash
  - что именно выкатили
  - какие проверки дали `200`
